# Known issues and follow-ups

Technical issues found while building the project, one line each. Labels in
parentheses (`C4`, `W19`, `VR7`, ...) are historical build-phase names kept so
the notes can be matched to the code comments.

- Testing/parity: the spec's "1e-3 max relative error per stage" is tighter than fp32 backend noise — the same SHARP model on CPU vs MPS differs by up to 1.8e-3 relative per element (8.7 on pre-activation deltas); pin the golden device and reconsider the criterion (`docs/research/sharp-reference.md` §10).
- Testing/parity: do not compare `.ply` quaternions elementwise — q and -q are the same rotation and the reference's scipy SVD picks signs unstably; compare covariance matrices or canonicalise signs.
- Build: `third_party/miniz` has no CMake target and is missing the CMake-generated `miniz_export.h`; the static library is now built from `core/CMakeLists.txt` (the zip reader needs it on every build) with the shim in `core/common/miniz_export.h`. Moving both under `third_party/` would still be tidier.
- Build: `core/CMakeLists.txt` globbed `core/*/*.cpp` only, so the new nested dirs `core/recon/ggml/` and `core/recon/fallback/` needed a second glob pattern; replaced by an explicit source list if the component set ever stabilises.
- Build: fixed in F1 — `tools/convert` and `tools/reconstruct` no longer hang off `SPLAT_HAVE_VULKAN`, and `-DSPLAT_USE_VULKAN=OFF` exercises the CPU-only path in CI.
- Fallback/C4: on MoltenVK the fp32 graph matches the CPU reference to cosine 0.99999 but per-element relative error reaches ~0.1 in the ViT taps (accumulation order). It is reported, not gated (spec: MoltenVK is not a parity target); repeat on RADV before Spike A signs off.
- Fallback/C4: Depth Anything's relative depth decays to 0 on sky, so `max_depth_m` (default 100 m) caps the metric mapping — without it the far background becomes kilometre-wide splats.
- Fallback/C4: HF `fusion_stage.layers.N` runs deepest-first (N=0 is the reference `refinenet4`); all four blocks have identical shapes, so a swapped order loads without an error. Noted in `tools/golden/README.md`.
- Renderer: the desktop viewer still disables window resizing (`GLFW_RESIZABLE`, false) and treats `VK_ERROR_OUT_OF_DATE_KHR` as fatal; swapchain recreation on resize is a C6 gap, not a math bug (review F1 rated it low).
- Renderer: with SHARP's `eps2d = 0`, a Gaussian whose 3-sigma quad contains no pixel centre draws nothing; gsplat's axis-aligned rectangle has a one-pixel minimum, so sub-pixel splats are the one remaining systematic difference from the reference (well under 0.1 % of the alpha mass).
- Public readiness: `platform/ps5/hello/hello.elf` and `platform/ps5/vk_hello/*.elf` are build outputs that embed absolute paths; they are regenerated by `make` and must never be committed (add `*.elf` to `.gitignore`).
- Public readiness: `AGENTS.md` quotes a mounted-volume path example inside the "never write personal paths" rule, so the public-readiness grep always lists that line; reword it to keep the check zero-noise.
- CI/docs: `README.md`'s Linux package list predates the CI fix — GLFW 3.4 builds both Linux backends and needs `libwayland-dev` (wayland-scanner) and `wayland-protocols`, otherwise configure fails at `third_party/glfw/src/CMakeLists.txt` ("Failed to find wayland-scanner").
- CI: lavapipe reports subgroupSize 4, so `VulkanContext::create` rejects it (renderer needs 32 or 64) and the GPU cases skip in CI; lavapipe advertises `subgroupSizeControl`, so requesting a 32-wide subgroup at pipeline creation would turn those cases into real coverage.
- Parity/C3: `monodepth` (041) sits on the reference's own `clamp(disparity, 1e-4, 1e4)`: ~3% of photo02/03 pixels are pinned at 1e-4, where a one-quantum disparity change is a 50% relative depth change (fp16 full-range cosine 0.9950, max abs 3336 m). Gate on the <=100 m range the initialiser keeps; the full-range numbers are still printed.
- C3/C4 shared: stb's nearest-neighbour chroma upsampling costs ~3 dB of end-to-end image PSNR on photo01 versus feeding PIL's pixels (35.16 vs 38.25 dB); a bilinear-chroma stb build would recover it for both backends.
- C3: the Gaussian decoder's fp16 weights are 10x more exact on ggml-vulkan (cosine 0.9999998) than on ggml-cpu (0.9999) for the same graph; the CPU gate is the 0.999 cosine, but the asymmetry is worth knowing when CI runs the fp16 case.
- Spike A: ggml-vulkan waits on its fences with `UINT64_MAX`, so a lost device hangs the payload; the bench watchdog bounds it from outside (exit 3, leak), but a `GGML_VK_FENCE_TIMEOUT_MS` in the five waits belongs in `patches/ggml/` once the tree is quiet.
- Spike A: the payload submit counter relies on `-Wl,--wrap=ggml_backend_graph_compute`, which macOS `ld64` lacks, so a host smoke build reports 0 submits (`-DSPLAT_BENCH_NO_WRAP`); harmless for the console, worth a `ggml_backend_set_submit_hook` if host runs become routine.
- Fallback/C4: the capture-pose PSNR ceiling at 500k Gaussians is ~21-24 dB on the detailed 1280x720..964 inputs (a box downsample to the 1.4-1.6 px grid plus a *nearest* upsample reaches only that), so the 28 dB target there needs >1M splats or a sharper-than-Gaussian reconstruction; `docs/fallback.md` has the numbers.
- Renderer/C7: the capture-frustum fade's inner ramp (`capture_inner_margin` = 0.02 of the capture image) costs ~1 dB of capture-pose PSNR and lifts dark border pixels by ~0.2 on both backends (SHARP's 1.ply shows the same band); a per-scene "opaque border" flag, or `inner_margin = 0` for scenes whose border splats are strong, would remove it (`docs/fallback.md`).
- Fallback/C4: one depth layer cannot fill the disocclusion behind thin foreground objects at ±5 cm parallax (photo01's rifle washes into the wall); the second depth layer C3 already produces is the fix, not the footprint.
- C5: `SplatScene`'s comment says "struct-of-arrays", but the 14 values are interleaved per Gaussian (`position[index*3+c]`), and `docs/formats/psplat.md`'s block table reads as if x/y/z were three separate `count`-long arrays; readers are consistent with the bytes, only the documentation is wrong (found off-by-one-block while verifying the SHARP intrinsics).
- Fallback edges at ±5 cm, left after the ramp-snap pass (`$SPLAT_DATA_DIR/runs/fallback_rootcause.md`, renders `runs/render/fallback5/`): a near object's bright rim that both the depth and the colour put on the background stays behind as a thin pale line (venice5 gunwale highlight at −5 cm, photo03 blue jacket); the extrusion fill reads as horizontal streaks in wide gaps and copies small bright objects right behind an edge (white streak beside photo03's bald man at +5 cm); ~200 px of short 1–2 px cracks remain in photo03.
- Fallback/C4 testing: with `SPLAT_FALLBACK_PHOTO=photo02_street.jpg`, `fallback reconstructs a splat scene from a photo` fails its "median splat depth 3.0 ± 0.6 m" check before and after the ramp pass (4.35 → 4.13 m): sky pixels below `kMinDisparity` are excluded from the median that sets the scale, so the scene median is farther than 3 m by design.
- Fallback/C4 (visual check of fallback5): venice5 +5 cm, dark drip blobs under the left half of the arch edge.
- Fallback/C4 (visual check of fallback5): venice5 capture pose, small dark bumps on the left edge of the tall mooring pole (~x1165, y780-895).
- Fallback/C4 (visual check of fallback5): photo03 +5 cm, pink strap-coloured smear with black dots right of the black-coat woman.
- Fallback/C4 (visual check of fallback5): photo03 −5 cm, dark navy block between the blue jacket and the bald man.
- C3 shared: `platform/ps5/ggml/bench_env.cpp` still carries its own `human_bytes` (the fifth copy); `splat::human_bytes` from `core/common/bytes.h` would replace it — left in place by F8 because `platform/ps5` was outside that task's area.
- Viewer/V1: the VideoOut frame is written by the CPU (the renderer's image → a host-visible RADV buffer → 64 KiB R_X tiles), logged as `copy=`/`tiles=`; a compute pass writing the tiles straight into the VideoOut buffer (imported with `VK_EXT_external_memory_host`) removes both, and RADV cannot scan out its own images because Mesa's scanout layout flag is WSI-private (`wsi_common_videoout.c`), so the round trip returns if PS5_Mesa ever exposes it.
- Viewer/V1: no DualSense input in the viewer title (Options to quit needs a user-service handle the title does not open); the run length comes from `SECONDS=` in `/data/ps5-splat-vr/bench/viewer.env` and `title.sh stop` ends a run through the quit file.
- VR1: native 90 Hz (`EnableVrMode`/`ConfigureOutput` `0x2000c`, no `SetRenderConfig`) is one line in `hmd2` and untested; the display path is proven only at 60-rendered-into-120.
- VR1: no TV mirroring (`sceHmd2ReprojectionSetMirroringOption` + `EnableMirroring`), so the TV keeps the console UI during a headset-only run; HLA-PSVR2 has the sequence in `psvr2.c` `mirror_apply`.
- VR1: eye poses at `sceVrTracker2GetResult` +0xa0/+0xe0 are unused; `hmd2` reports only the device pose, so the pattern is drawn from one midpoint, not per-eye.
- VR1: the title program and `hmd2` use the shared 13.60/7.61 export tables, so a 90 Hz or mirroring probe that needs another export is a table edit (`tools/export-tables/`), not an API discovery.
- Viewer/V1: the title's `sce_module/libc.prx` is still PS5VR's published copy (SHA-256 pinned by the build) and the converter is the macOS dev-loop binary; a release must build both from source (`PS5_Vulkan`'s `make libc`, `tools/build-native.sh`), as `platform/ps5/title/README.md` says.
- `title.sh install` never creates the package root itself (`list_dirs` skips the `""` entry), so a first install on a console without `/data/homebrew/<TITLE_ID>` stops at `HTTP 500 mkdir …/sce_module`; create the root (`POST /api/ftp/mkdir`) or add `""` to the mkdir loop (hit in console session 2 for both PPSA99200 and PPSA99201).
- Console config: ShadowMountPlus is running but binds its HTTP API to loopback (`[CFG] api=127.0.0.1:10101` in `/data/shadowmount/debug.log`), so `title.sh install` always exits 3 at the scan; the 15 s auto-scan still registers a folder under `/data/homebrew`, so `title.sh status`/`launch` work after ~15 s. Fix the console's `config.ini` (`api_bind_address`) or make `title.sh` treat the scan as optional.
- `run-bench.sh --title` reads its klog window to the end even after the bench's `done, exit` line (no early break in the capture loop), so a 1200 s window always costs 1200 s wall time; the bench time is the payload's own line, not the command's duration.
- `run-viewer.sh` (through `title-capture.py`) has the same no-early-break loop: it records the `viewer: done, exit` line but keeps streaming until the window closes, so a `--seconds 45` run costs 135 s of wall clock (console session 3, two runs, 140 s and 144 s each).
- Uninstall/CL1: `title-uninstall.sh --yes` refuses (exit 3) while ShadowMountPlus is loopback-bound — there is no remote way to call `sceAppInstUtilAppUnInstall` otherwise; fixing `api_bind_address` in `/data/shadowmount/config.ini` (the scan-path entry above) unblocks both it and `title.sh install`.
- Uninstall/CL1: `/system_ex/app/<ID>` cannot be inspected through ProsperoMgr's file API — `GET /api/ftp/list?path=/system_ex/app/PPSA99200` returns `entries: []` whether the title is mounted or not — so "the runtime mount is released" is inferred from the uninstall call, not verified.
- Uninstall/CL1: whether `sceAppInstUtilAppUnInstall` also removes `/user/app/<ID>` and `/user/appmeta/<ID>` on 13.60 is unproven (the ftpsrv installer re-`mkdir`s `/user/app/<ID>` right after an uninstall, which suggests the directory does go); the tool reports them and exits 6 rather than deleting outside `/data/homebrew/<ID>`.
- Renderer/C6: `RendererOptions::eye_center_shift` is new for VR2 — a per-eye principal-point x offset in pixels, needed because PSVR2's frustum is asymmetric (Hmd2 reports tangents 1.842 out / 0.947 in, i.e. ±318 px at 1984 wide) which one shared `cx` cannot express; the desktop stereo path passes 0, so nothing changed there.
- Viewer/VR2: the capture-frustum fade keeps the *first* scene's capture intrinsics across an L1/R1 switch (the renderer copies them at create), so switching between scenes shot with different cameras fades slightly wrong; `viewer: vr note:` says so when the intrinsics differ.
- Viewer/VR2: TV mode (`MODE=tv`) in the viewer package now runs under the PS VR2 identity (attribute `0x62000000`, attribute3 `0x4080c40`, VR-only bit set) because VR is the default; whether the TV's VideoOut path still works in a VR-only title is unverified — a TV-only build would need a param.json without the `0x800` bit.
- hmd2/VR1: the per-eye poses at `sceVrTracker2GetResult` +0xa0/+0xe0 are read now, but only for the IPD and the eye midpoint; a per-eye *orientation* the tracker reports is ignored (the renderer models eyes as a lateral offset along camera right).
- Renderer/VR2: `SplatRenderer::render` waits 10 s on its fence (core's existing bound), while the VR eye-buffer handoff waits 500 ms; a wedged GPU is therefore reported by the copy first. Worth one timeout option if VR ever needs the frame-level bound to be tight.
- Viewer/VR2 (visual check, `runs/vr2_fix/after/`): at the placement pose the SHARP photo covers only ~13.5 % of the PSVR2 eye — the capture is 30° half-FOV horizontally and ~23° vertically, the headset is ~61°/53° — so the photo sits as a small upright rectangle in a wide grey field. A "fill the view" mode (default world scale/zoom or a framed panel) is a product decision, not a bug.
- Viewer/VR2: the new VR comfort default (`kDefaultVrComfortRadius` = 2 m) keeps a 1 m free zone; the capture-frustum fade still darkens the edges of the photo as soon as the head leaves the capture point, so a standing user can walk out of the photo's valid volume while the comfort fade is still 1. The capture-frustum fade is the correct guard there; the radial fade mainly protects against torn geometry.
- TV viewer mode runs at 39.9 fps on the console although the GPU needs ~3.4 ms per frame (console session 6, 2026-10-26); likely the CPU copy into the tiled VideoOut buffer. Matters only for the TV mode.
- vk_hello still carries its own copies of result_name, a memory-type loop and now_ms (platform/ps5/vk_hello/main.cpp:131,138,557; one-app review 2026-10-26); fold into platform/ps5/viewer/vk_common.h / title_common.h when vk_hello is next touched.
- Runbook/console: the preflight says the title route needs "a HEN (OnionHEN/etaHEN)" between kstuff and ShadowMountPlus, but the console has no HEN loaded at all (no HEN process, no `/data/OnionHEN`/`/data/etaHEN`, 9081 and 1337 closed, autoload chain is kstuff -> nanodns -> shadowmountplus -> ProsperoMgr), and the title route works — fix the preflight wording and note that route A therefore needs OnionHEN installed first (measured 2026-10-26, `runs/p1_probe/`).
- Viewer/VR4: `run-viewer.sh`'s header still lists `COMFORT_RADIUS=0.25` as if it were the VR default (it is the desktop value and fades the scene from 12.5 cm; the VR default is `kDefaultVrComfortRadius` = 2 m) — the runbook now warns, the script's usage comment should drop the example.
- Hmd2/VR4: the SetParam layer field at `+0x98` (`100`) is copied from HLA-PSVR2 without a known meaning (`psvr2.c:1581` writes the same constant); if a future reprojection artefact looks like a fixed scale, that field is the first thing to sweep.
- Docs/render.md still says world scale is clamped 0.25x-4x and that an R3 press recentres; VR5 raised `kMaxWorldScale` to 8 and moved VR recentre to a 1 s Cross hold, and VR6 put the range back to 0.25-4 and made scale in place (no pivot translation) — the renderer doc needs a pass.
- Viewer/VR5: the scene label is scaled by moving its world quads (its R8 text mask is not re-rasterised), so at 8x the glyphs are geometrically larger but soft; a re-raster at a screen-space size would keep them crisp if the label matters at extreme scales.
- Compare/models (2026-10-26): the DA2 comparison scenes (`runs/compare_sharp_vs_da2*`) sit at the fallback's 3 m assumed scale while SHARP's are metric (per-pixel median 7-80 m), so their ±8 cm backdrop percentages measure the scale difference, not the fill; a matched-scale or matched-parallax pose would make that table fair.
- Compare/models: no depth model is a metric reference — MoGe-2 is 1.27-1.59× SHARP's depth on the outdoor photos but 5.3× too far on the 0.4 m pizza close-up, DA3-Metric-Large is 0.28-0.36× on the outdoors (its metric head saturates ~45 m) and 0.80× on the close-up; a scene's absolute scale therefore decides how much a head move reveals (see `runs/compare_models/REPORT.md` §5).
- Fallback/C4: the 500k grid stops exactly at the photo border, so at ±8 cm almost all of the visible pure backdrop is the frame-edge strip (photo 1: 0.205 % full frame vs 0.001 % inside a 60 px border, MoGe-2 scene); extending the outermost cell layer outward by the disocclusion band would remove it, and SHARP's Gaussians already overshoot the frustum.
- Fallback/C4: at SHARP's own density (1.18M splats) the same MoGe-2/DA3 depth maps gain 1.2-3.0 dB capture PSNR and stay 4-5 dB behind SHARP, so the 500k builder — not the depth encoder — is what separates the fallback from SHARP at the capture pose.

- Viewer/VR4: the new scene names (`immichvr-N-moge2`, `-da3-metric-large`, `-da3-small`) are mapped in `core/render/scene_label.cpp`, but the console still runs the pre-change viewer title, so its label says "SHARP" for them until the title is rebuilt and reinstalled.
- Viewer/VR6: `median_scene_depth` is dominated by the background of these scenes (25-50 m, clamped at 50) because it samples every splat, so the "scene centre" it names is the far backdrop, not the subject; a content centre (e.g. a lower percentile or the depth of the densest bin) would be a better name if a feature ever needs it — scaling no longer uses it as a pivot.
